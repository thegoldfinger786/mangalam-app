# Mangalam — Project Constitution & Standing Guidelines

This file is the permanent, authoritative memory for this repository. It is built from three sources: the actual implementation as discovered (see [`docs/DISCOVERY.md`](docs/DISCOVERY.md)), the business/product vision as given by the founder, and the tensions between the two (see [`docs/VISION_ALIGNMENT.md`](docs/VISION_ALIGNMENT.md)). Read those two documents for the full evidence trail; this file states the rules that follow from them.

**Meta-principle, applies to every section below:** optimize for consistency over novelty, prefer evolutionary change over revolutionary redesign, and assume this project is still running in 10 years. When in doubt, extend an existing pattern rather than introduce a new one. When a genuine conflict exists between the current implementation and the stated vision, this document says so explicitly rather than picking a side — those items require an explicit product decision, not a unilateral engineering or content call.

**How to work on this repository:** read [`docs/Project_instructions.md`](docs/Project_instructions.md) before starting. It defines the expected working style for coding agents — outcome-oriented rather than process-prescribed, verification effort scaled to risk, and a bias toward deciding and proceeding once evidence is sufficient. This file (`CLAUDE.md`) says *what* the project is and what the rules are; `Project_instructions.md` says *how* to go about changing it.

**Security posture:** [`docs/SECURITY_REMEDIATION.md`](docs/SECURITY_REMEDIATION.md) is the living record of the 2026-08 security remediation — findings and their status, the authorization architecture, inventories of Edge Functions, database objects and storage buckets, and the decision log. Read it before touching authentication, Edge Functions, RLS, storage policies, or credentials. It also documents the three subsystems (APP / CONTENT_PRODUCTION / MEDIA_AUDIT) and records that production contains tables, functions and buckets that this repository does not — so absence from the repo is never evidence that something is unused.

**UX & design posture:** [`docs/UX_REVIEW.md`](docs/UX_REVIEW.md) is the 2026-08 screen-by-screen product review, [`docs/UX_TRACKER.md`](docs/UX_TRACKER.md) is the living backlog of every finding (with status and a decision log), and [`docs/DESIGN_PRINCIPLES.md`](docs/DESIGN_PRINCIPLES.md) states the durable Mangalam design principles — including the "inclusive spiritual-wellness experience, not a religious app" positioning. Check the tracker before any UX/design change: relate the change to an existing finding and update that item rather than creating a duplicate; preserve original findings even when a recommendation is later deferred or rejected. [`docs/TESTING.md`](docs/TESTING.md) covers how to run the app and the dedicated QA test account.

## 1. Project Constitution

**Mission:** Mangalam is the daily companion for wisdom, reflection, and spiritual growth — "ancient wisdom for modern life." It is not a scripture repository or a quote app. Every piece of content exists to answer a practical question ("how does this apply to my work / my relationships / my family / my decisions today"), not to explain philosophy for its own sake.

**What Mangalam is:**
- An audio-first, daily-habit product (narrated Sanskrit/story + translation + commentary + practical application, in English and Hindi).
- The long-term destination in a wider content ecosystem that also includes podcast, YouTube, and a website — this app is where users go for structured, sustained engagement, not just discovery.
- Built to last a decade. Every identifier, schema decision, and content convention should be made as if it will still be load-bearing in 2036.

**What Mangalam is not:**
- Not a preachy, sectarian, political, fear-driven, or sensationalist product.
- Not (currently) a personalization engine, a course platform, or a subscription business — those are named future directions, not present-day scope.
- Not a place for ad hoc, undocumented schema or content changes — see §4 and §6.

**Standing tensions — decisions recorded 2026-07-15 (see `VISION_ALIGNMENT.md` §6 for full detail):** the free-tier session cap and the devotional sign-off convention are now **resolved** — the app stays free indefinitely (monetization via donation/product-sales, not usage gating) and the devotional sign-off is a deliberate brand choice, not something to soften. The LLM-embellished Ramayan/Mahabharat "Story" label and the fixed office/home-only examples remain **acknowledged gaps, deliberately deferred** — not to be retrofitted onto existing content/audio, but to be addressed for *future* episodes and verses. The content-ecosystem question (§1.5) is also resolved: live YouTube (English/Hindi Gita), Spotify (English/Hindi Gita), and website (mangalamapp.com) channels already exist outside this repo, run through a separate process — this codebase has no automated export pipeline to them today. Anyone touching these areas should re-read `VISION_ALIGNMENT.md` §6 first.

**Decision-making default:** when a new requirement could be met either by extending something that already exists or by building something new and parallel, extend the existing thing. The one prior exception to this in the codebase's own history (`episodes`/`episode_content` → unified `verses`/`verse_content`, see migration `20260315113335_drop_episodes_tables.sql`) was a deliberate, one-time consolidation — it is not license for repeated schema forking.

## 2. Engineering Guidelines

- **Directory structure:** all application code lives under `src/`. The root-level `components/`, `hooks/`, `constants/` directories are unused Expo template scaffolding — do not add to them or resurrect them; new code always goes in `src/components`, `src/hooks` (if introduced), etc.
- **State management split:** keep the existing two-store separation. `useAppStore` = persisted session/preferences/onboarding state (anything that should survive app restarts and represents "who the user is / what they've set"). `useAudioStore` = live, ephemeral playback-engine state (never persisted directly, rehydrated from `AsyncStorage`/remote progress on load). Do not introduce a third global store that blurs this line; if new global state doesn't cleanly fit either, that's a signal to think about which one it actually is.
- **Theming:** all new UI must consume `useTheme()` (`colors`, `spacing`, `typography`, `borderRadius`, `layout`) rather than hardcoded values. If you need a new token, add it to `baseTheme` in `src/theme/index.tsx`. (`src/theme/spacing.ts` — a stray duplicate ramp — was deleted 2026-08-31; don't recreate a parallel spacing file.)
- **Typography:** never write a bare `fontSize:` / `fontWeight:` in new code. Use `<AppText variant="…">` (`src/components/AppText.tsx`) with a semantic role from `src/theme/typography.ts` (`display` / `title` / `heading` / `subheading` / `body` / `bodySmall` / `caption` / `label` / `button`), layering colour / alignment on top via `style`. Roles carry device scaling (`fontScale()`, a gentle clamped curve — not a flat width multiplier) and an accessibility `maxFontSizeMultiplier`. An explicit size is allowed only for a genuine component constraint no role fits (fixed badge, native-control parity) — comment why and still pass a cap. Full rules in [`docs/DESIGN_PRINCIPLES.md`](docs/DESIGN_PRINCIPLES.md) § Typography.
- **Styling pattern:** continue the existing `const createStyles = (...) => StyleSheet.create({...})` factory pattern, memoized with `useMemo`, taking the relevant theme slices as arguments. Dynamic/resolved values (actual color values, conditional styles) stay inline in JSX; static layout values stay in the stylesheet.
- **Logging:** always use `src/lib/logger.ts` (`logger.log/warn/error/debug`), never raw `console.*`, in any shipped `src/` code. `logger.error` is the only channel that reaches Sentry in production — use it for anything that should be visible in crash reporting, and pass `context`/`tags` consistently with existing call sites.
- **Identity vs. classification:** the pattern in `src/lib/bookIdentity.ts` is a hard rule, not a suggestion — `book_id` (and any future analogous `*_id`) is the only field allowed to drive navigation, fetch, or playback logic. `slug`/`code`/`content_type` are classification fields for feature flags and display only, and must be resolved through the identity-cache helpers (`getBookCode`, `isGita`, etc.), never hardcoded as string literals in screen code. Apply this same identity/classification split to any new top-level entity introduced later (e.g., if "journeys" or "personas" become real entities).
- **No orphaned parallel implementations:** if a new implementation replaces an old one (as `LoginScreen` replaced the email/password flow in `AuthScreen.tsx`), either remove the old one or explicitly wire it back in with a stated reason — don't leave two live, divergent implementations of the same concern where only one is reachable. (`AuthScreen.tsx` is an intentional exception, confirmed 2026-07-15: Google/Apple sign-in is the only user-facing auth path; the email/password `AuthScreen.tsx` is deliberately kept unrouted as a hidden admin/test entry point, not orphaned dead code awaiting a decision.)
- **Secrets:** never commit an API key, service-role key, or credential to source, in any language, in any script — including "just for local testing." Load everything from environment variables (`process.env`/`Deno.env.get`), following the existing `dotenv` pattern already used by every script except the one that violated it. `EXPO_PUBLIC_*` variables are the only ones ever allowed to ship inside the client bundle; service-role/API keys belong only in edge functions and local/CI script environments, never in `src/`.
- **Migrations, not dashboard edits:** every schema change, from now on, must be a tracked file in `supabase/migrations/` with a timestamped, descriptive filename — no more direct SQL-editor or dashboard changes that bypass version control. This is the single hard rule this document adds that the codebase's own history did not previously follow (see the untracked base-schema gap in `DISCOVERY.md` §3).
- **Script hygiene:** before adding another one-off script to `scripts/tools/`, check whether an existing script can be parameterized instead (several near-duplicate preview/retry scripts already exist). This is a preference, not a blocker — don't let it stop urgent one-off work, but default to consolidating when convenient.
- **Testing/CI:** none exist today; that is acknowledged debt, not something this document mandates fixing in one pass. Prefer adding verification incrementally around new or changed logic (the `/verify` skill pattern) over a big-bang retrofit — consistent with evolutionary-over-revolutionary.

## 3. Product Principles

- **Practical application is not optional.** Every piece of content ships with `daily_life_application` and `practical_examples` — this is the product's core differentiator versus a plain scripture-reading app and must not be dropped for any content pillar, present or future.
- **Daily habit over binge consumption.** Streaks, resume-journey state, and background/lock-screen playback exist to support a short, daily ritual, not long consumption sessions. New features should be evaluated against "does this help someone come back tomorrow," not "does this maximize session length."
- **Content-layer transparency is a product commitment, not a UI nicety.** Users should always be able to tell what's original text, what's translation/story, what's commentary, and what's practical interpretation. This is fully honored today for Gita. It is not fully honored for Ramayan/Mahabharat, where LLM-invented sensory/emotional detail is shown under a plain "Story" label with no disclosure (`VISION_ALIGNMENT.md` §1.4) — new narrative-pillar content (character journeys, hidden stories) should not silently repeat this gap without an explicit decision on how (or whether) to disclose the interpretive layer.
- **English and Hindi are the current, deliberate scope.** Adding a language is a real content-strategy decision (new prompts, new purity rules, new voice mapping, new QA), not an incidental engineering task — treat it with the same weight as adding a new scripture pillar.
- **The free experience is the product, indefinitely — confirmed 2026-07-15.** This is no longer a phase-dependent stance: the app stays free for all users, with monetization via donations (and possibly future product sales) rather than usage gating. The dormant "3 sessions/day" cap in `PlayScreen.tsx` is dead code to be cleaned up when convenient, not a paused feature — do not re-enable it without a new, explicit product decision reversing this one.
- **New scripture/content pillars extend, don't fork.** Upanishads, Puranas, and future "character journeys" or "hidden stories" should be modeled as new `books` rows using the existing `verses`/`verse_content`/`verse_audio` shape (already anticipated — see `ContentPath` in `src/data/types.ts` and the "coming soon" tiles in `HomeScreen.tsx`), not a parallel content model. If the `verse_no`/`sanskrit` naming genuinely stops fitting non-verse narrative content, that naming question should be raised deliberately (see §7), not solved by forking the schema again.
- **Persona-aware content is a real future direction, not a present capability.** The vision names five distinct audiences (young professionals, diaspora, parents, spiritual seekers, beginners); the current pipeline generates one fixed pair of examples (office + home) for everyone. Building persona-specific content is a deliberate schema + content-strategy expansion (see §6), not something to bolt on ad hoc into the existing two fixed slots.

## 4. Database Standards

- **All schema changes are migrations.** Every `CREATE`/`ALTER`/`DROP` goes into `supabase/migrations/<timestamp>_<description>.sql`, checked in with the same PR as the code that depends on it. `src/lib/database.types.ts` must be regenerated after every schema change so it stays the authoritative, accurate reflection of the live schema — no drift between the generated types and reality.
- **RLS is enabled at table-creation time, not retrofitted.** The migration history shows RLS and policy hardening being added *after* several tables already existed in production (`20260305_fix_rls_warnings.sql`, `20260305_security_performance_hardening.sql`). Do not repeat that sequencing — every new table's initial migration must enable RLS and define its policies in the same migration, not as a follow-up pass.
- **Naming conventions (continue as-is):** `snake_case` columns; `<entity>_id` as both primary key name and foreign key name (`book_id`, `verse_id`) — never a bare `id` for a top-level entity that other tables reference; two-letter language codes (`en`/`hi`) everywhere language appears; `status` columns use short lowercase state words (`processing`/`ready`/`failed`, matching `verse_audio.status`).
- **No new legacy shadow tables without a retirement plan.** `audio_cache` exists alongside the newer `verse_audio` canonical registry, written to "for legacy compatibility" with no scheduled removal. If a new canonical table is introduced to replace an old one, the migration or a companion doc must state how and when the old one gets retired — don't let two parallel write paths accumulate indefinitely.
- **No phantom or dead columns.** `books.code` is referenced in application code (`bookIdentity.ts`) but does not exist in the schema, silently falling back to `slug` on every lookup. When a planned column doesn't get built, remove the code path that assumes it exists (or build the column) — don't leave both states half-true.
- **`SECURITY DEFINER` functions must set `search_path` explicitly**, following the existing hardening (`ALTER FUNCTION ... SET search_path = public`). Any new `SECURITY DEFINER` RPC must do this in the same migration that creates it, not as a follow-up fix.
- **Views for read-side denormalization only.** The `canonical_*` views and `verse_content_full` are an acceptable, continued pattern for reporting/aggregation reads — they are not a substitute for tracked migrations of the underlying tables, and their own defining SQL should itself live in a tracked migration going forward (today it does not — see `DISCOVERY.md` §3 gap).
- **Identifiers are permanent.** `book_id`, `verse_id`, and any future top-level entity ID must never be reused or reassigned to a different logical entity once issued — external systems (podcast/website/future integrations), user bookmarks, and progress records will reference these for the life of the product. Renaming a `slug` or display title is fine and cheap; changing what a `book_id` refers to is not.

## 5. AI Usage Policies

- **Two vendors, by design, not by accident: Google Gemini for text generation, Google Cloud TTS for audio.** Don't introduce a second LLM or TTS vendor for the same purpose without a strong, explicit reason — consistency of voice, pronunciation, and content style across the entire catalog depends on a single generation pipeline.
- **Prompt templates are content-policy documents, not just strings.** `GEMINI_PROMPT`, `MAHABHARAT_PROMPT` (in `supabase/functions/import-content/index.ts`), and `scripts/tools/mahabharat_prompt.md` encode real product decisions — word counts, tone rules, the Hindi purity/no-Urdu-loanword list, the "recreate and expand" instruction for narrative content. Changes to these should be treated as deliberate content-strategy decisions (reviewed the way you'd review a change to brand voice guidelines), not casual prompt tweaks.
- **Automated quality gates are mandatory, not optional, for any new generation pipeline.** The existing retry-with-validation loop (`validateHindiTransliteration`, up to 5 attempts with backoff) is the standing pattern — any new language, pillar, or content type added to the generation pipeline must ship with an equivalent automated check before content is marked `ready`, not rely on manual QA alone.
- **No hardcoded credentials, anywhere, ever** — this is restated here because it has already been violated once (a live Gemini key hardcoded in `scripts/tools/preview_english_verse_robust.py`). Every script and edge function loads keys from the environment.
- **Content correction path: prefer regenerating over hand-editing.** The default way to fix a piece of content is to re-run the generation pipeline (`generate-tts`/`import-content`, possibly with `force: true`). Hand-written SQL `UPDATE` batches (like `scripts/reference/ramayan_updates.sql`) are an accepted exception path for urgent, targeted fixes — but they must be saved/archived for auditability (as already practiced) and are not the default workflow.
- **Idempotency and caching are load-bearing, not incidental.** The `status: processing/ready/failed` state machine and the "skip regeneration unless the source changed or `force: true`" check in `generate-tts` exist to avoid unnecessary API cost and to avoid clobbering good audio with a re-run. Any new content-type pipeline must preserve this shape.
- **Extending the "recreate and expand" narrative-embellishment pattern to new pillars is a decision, not a default.** The instruction that produces Ramayan/Mahabharat's invented sensory detail and character inner-monologue should not be silently copy-pasted into new prompts for Upanishads/Puranas/character journeys without confirming that's the intended creative latitude for that pillar (see §3 and `VISION_ALIGNMENT.md` §1.4).

## 6. Content Creation Guidelines

- **Every content unit's shape, per language:** source text (Sanskrit verse, or blank for pure narrative content), a narrative rendering (translation for verse-based content, story for narrative content), commentary, daily life application, practical examples, and a synthesized audio narration. This is the non-negotiable minimum for any new piece of content in any pillar.
- **Existing structural constraints continue as the standard** unless deliberately revised for the whole catalog at once: ~500–700 word narrative/story, ~100–150 word commentary, short spoken sentences, no flowery/complex prose, natural-punctuation pacing instead of explicit SSML breaks in authored text.
- **Hindi purity policy is a living brand-language standard, not a one-off script rule.** The no-Urdu-loanword / no-English-transliteration list in `import-content/index.ts` should be treated as an evolving style guide — reviewed and extended periodically, not just enforced as dead code.
- **Layering discipline by content type:**
  - Verse-based scripture (Gita today; Upanishads if/when added) — keep the existing four-way separation: source verse, translation, commentary, application, each independently labeled in the UI.
  - Narrative/epic content (Ramayan, Mahabharat, and any future character journeys / hidden stories) — continue producing LLM-expanded narrative as today, but any *new* pillar of this type should decide, explicitly, whether and how to disclose that the "Story" text includes invented detail beyond the base source. Existing Ramayan/Mahabharat content is grandfathered under the current convention pending a business decision; don't retroactively relabel it without one, and don't extend the undisclosed pattern to new pillars without confirming it's intended.
- **The devotional sign-off (`Jai Shri Krishna` / `Jai Shri Ram`) is today's convention for existing pillars, not an automatic template for new ones.** Upanishads and Puranas don't have a single obvious deity-specific sign-off the way Gita/Mahabharat (Krishna) and Ramayan (Ram) do. Don't default-copy a deity-specific exclamation into a new pillar's content template without an explicit decision — this is exactly the kind of choice `VISION_ALIGNMENT.md` §1.3 flags as unresolved.
- **Practical examples: today's template is two fixed slots (office/workplace + general life/home), or one slot for Mahabharat's sign-off style.** Introducing persona-specific examples (parenting, leadership, relationships, diaspora-specific) is a deliberate schema and prompt-template expansion — when it happens, add a real domain/persona tag to the data model rather than overloading the existing two fixed fields with more implicit meaning.
- **All generated content must pass through the existing validation loop before being marked ready.** Manual SQL edits remain an exception path, archived under `scripts/reference/` for auditability, exactly as done today — not a substitute for the generation pipeline as the primary editing workflow.

## 7. Future Architectural Principles

These are for the next decade, not the next sprint — stated so future contributors don't have to rediscover them by trial and error.

- **Identifiers are forever.** Once a `book_id`, `verse_id`, or any future top-level entity ID is issued, its meaning never changes, even if display names, slugs, or classification codes change freely. Anything that might outlive this specific app (podcast episode references, website URLs, a future export format) should be built to reference these stable IDs, not slugs or titles.
- **Schema growth is additive, not forked.** New scripture pillars and new narrative content types extend the existing `verses`/`verse_content`/`verse_audio` shape. This already happened once by consolidating a separate `episodes` model into the unified one — treat that as the one allowed "big" schema consolidation for this decade, not a repeatable move. If `verse_no`/`sanskrit` naming becomes a genuine poor fit for pure narrative "episodes," that's a deliberate, well-scoped renaming/generalization project to propose explicitly — not a reason to introduce a second parallel content schema.
- **Content-as-platform: one source of truth across channels.** If/when podcast, YouTube, or website distribution pipelines are built (in this repo or elsewhere), they should be designed to consume the existing `verse_content`/`verse_audio` records (directly or via a well-defined export/API) rather than maintaining independently authored copies of the same content. Avoid content forking across channels from the start, since reconciling forked content later is far more expensive than designing for a single source now.
- **Personalization is an additive layer, not a content-model rewrite.** When persona/theme-based journeys are built, prefer adding a tagging/classification layer over existing verses (e.g., a many-to-many theme or persona association) over restructuring how content itself is authored and stored.
- **Monetization/entitlements, when built, must be backend-verified.** `accountStatus` today is a client-only Zustand flag with no backend counterpart and no connection to the Stripe donation flow. If real entitlements (premium journeys, memberships, family plans) are built, they need a real backend table + RLS-aware entitlement checks — not an extension of the current client-only flag.
- **Multi-language expansion reuses the existing two-letter-code column pattern** (`language` on `verse_content`/`verse_audio`) rather than introducing a parallel translation system or a different i18n mechanism for content vs. UI strings.
- **Testing/CI should grow incrementally alongside the codebase**, attached to new or changed logic as it's written, rather than attempted as a single retrofit — consistent with the evolutionary-over-revolutionary mandate for a 10-year-old codebase in the making.
- **Every hard rule in this document has exactly one enforcement mechanism worth protecting above all others: migrations are tracked, RLS is enabled at creation, and secrets are never committed.** If this document is ever trimmed for length in the future, keep those three.
